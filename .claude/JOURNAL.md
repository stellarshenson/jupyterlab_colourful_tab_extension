27. **Task - Reject minting our own stable tab id** (v1.1.13): user asked whether we could hook JupyterLab to generate a durable id to hold onto, rather than "patching / plumbing"<br>
    **Result**: Rejected. Minting is trivial - ANCHORING is the problem: after a reload the id must be looked up BY a stable identity, which is exactly the missing thing (circular). An id is only as durable as its carrier: files carry the path (already the key), terminals carry nothing (frontend `Terminal.IModel` is literally `{name: string}`; server adds only `last_activity`), launchers have no durable resource. Confirmed we sit at the platform ceiling - JupyterLab's own `WidgetTracker.restore` uses `name: e => e.context.path` and `name: e => e.content.session.name` (read from the built bundle), the same two tiers, so it conflates a recycled terminal identically. Also exposed a residual gap in entry 26's prune: it only catches WITNESSED deaths, so death + recycle while the page is closed still inherits (`last_activity` cannot disambiguate - advances for both). Only a server extension closes it, the sole observer outliving the terminals - rejected against the frontend-only architecture
