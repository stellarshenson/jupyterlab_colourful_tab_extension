# Defects - jupyterlab_colourful_tab_extension

`[ ]` open, `[x]` fixed. Dated notes under each track how it evolved.

## Active tab

- [ ] `DEF-1` **selected-tab accent bar disappears after a few seconds** - MEDIUM; the blue top accent bar (`.lm-TabBar-tab.jp-mod-current::before`, `tabs.css`) vanishes on coloured tabs while they stay selected, so the user cannot tell which tab is current; cause: our public API `setWidgetTabColour` overwrote `widget.title.className` wholesale, but the shell stores the accent by appending `jp-mod-current` to that same property (`shell.js` `_onCurrentChanged`); a consumer (jupyterlab_claude_code_extension) re-tinting on each title/status update destroyed `jp-mod-current`, and Lumino's next render (`createTabClass`) dropped the accent; menu-coloured tabs were unaffected because that path uses the DOM `classList`, not `title.className`; fix: `setWidgetTabColour` now tokenises `title.className`, drops old colour tokens, appends the new one, and preserves everything else; `src/colours.ts`
  - 2026-07-15 reported: "the accent bar disappears from the selected tab after a short while - confuses user, as user doesn't know which tab is selected"; screenshot shows a selected peach terminal tab whose blue accent later vanishes
  - 2026-07-15 hypothesis (WRONG): guessed JupyterLab-core focus behaviour dropping `jp-mod-current`, "not our bug"; user disproved it by testing - non-coloured and launcher tabs keep the accent, only coloured tabs lose it
  - 2026-07-15 root-caused: our API's `title.className =` overwrite destroyed the shell's `jp-mod-current`; triggered when the claude_code consumer re-applies the colour on title changes
  - 2026-07-15 fixed (pending runtime confirmation): non-destructive tokenised swap in `setWidgetTabColour`; jest 11 green incl. 3 accent-preservation tests, build + lint clean; awaiting browser confirmation before marking `[x]`; see [acc-crit Active Tab Colour](acc-crit-jupyterlab-colourful-tab-extension.md#active-tab-colour)

## Toolbar

- [ ] `DEF-2` **toolbar strip below the active tab stops matching its colour** - MEDIUM; the `jp-toolbar` `::part(positioning-region)` strip below the current widget's tab (the notebook/console toolbar) renders the pale base shade while the active tab renders the distinct `-active` shade, so the strip looks "uncoloured" next to the selected tab; regression introduced by 1.1.5: the active-tab feature added `.lm-mod-current.jp-colourful-tab-<id>` `-active` rules for the tab but no matching rule for the toolbar, so the unchanged base `.jp-colourful-tab-<id>::part(positioning-region)` rule keeps painting the toolbar the base shade; no one asked to remove the toolbar colour - the feature just moved the tab's shade and left the toolbar behind; fix: add `jp-toolbar`-scoped `-active` rules (`jp-toolbar.jp-colourful-tab-<id>`, its `*`, and `::part(positioning-region)`) - since `applyToolbarColour` only tints the visible (current) panel's toolbar, a coloured `jp-toolbar` is always the active one, so it matches the active tab; tabs are untouched (they are `<li>`, not `jp-toolbar`); `style/base.css`
  - 2026-07-15 reported: "we used to colour also another element below the tab - and now it isn't coloured for the active tab"; user pasted the `positioning-region` shadow div and confirmed the only recent changes were the accent-bar fix (DEF-1) and the active-tab shade, with no instruction to strip this part
  - 2026-07-15 root-caused: 1.1.5 gave `.lm-mod-current` tabs a distinct `-active` shade; the toolbar `::part(positioning-region)` is painted only by the base `::part` rules, so the current widget's toolbar stayed on the base shade and no longer matches its tab; determinable from CSS - no active `::part` rule exists
  - 2026-07-15 fixed (pending runtime confirmation): added six `jp-toolbar`-scoped `-active` rules in `style/base.css`; awaiting browser confirmation before marking `[x]`; see [acc-crit Active Tab Colour](acc-crit-jupyterlab-colourful-tab-extension.md#active-tab-colour)

- [ ] `DEF-3` **toolbar not coloured for API/claude_code tabs** - MEDIUM; a tab tinted through the public `setColour` API (e.g. `jupyterlab_claude_code_extension` on conversation restore) colours the tab but NOT the toolbar strip below it, so the bottom part stays blank; cause: `applyToolbarColour` (`src/index.ts`) sourced the colour from the menu-driven `tabColours` localStorage map only - API colours never enter that map, so `tabColours.get(stableId)` returned `undefined` and the function took its "clear all toolbars, colour nothing" branch, actively leaving the toolbar blank; the DEF-2 CSS fix could not help because the toolbar never received a `jp-colourful-tab-*` class in the API path; fix: `applyToolbarColour` now derives the colour from the active tab's live `classList` (`COLOURS.find(c => activeTab.classList.contains(c.cssClass))`), which reflects both the menu path and the API path since both land a `jp-colourful-tab-*` class on the tab element, so the toolbar follows either; `src/index.ts`
  - 2026-07-15 reported: "why does jupyterlab_claude_code_extension when restoring conversation still follow colouring without the bottom part?"; observed after 1.1.7 that claude_code-restored tabs colour the tab but not the toolbar
  - 2026-07-15 root-caused: the toolbar colour path (`applyToolbarColour`) was gated on the menu map; the public `setColour` API only sets `title.className` (tab class) and never populates the map, so API-coloured tabs got no toolbar colour - determinable from the two code paths
  - 2026-07-15 fixed (pending runtime confirmation): `applyToolbarColour` reads the colour from the active tab's live class instead of the menu map; awaiting browser confirmation before marking `[x]`

- [ ] `DEF-4` **colour bleeds onto other panels' toolbars in split layouts** - MEDIUM; with the main area split, a coloured tab in one panel paints the toolbar of a DIFFERENT panel; worst with API-tinted claude_code terminals - terminals have no `jp-toolbar`, so their colour always lands on some other widget's toolbar (e.g. the notebook in the adjacent split), which reads as "other tabs get coloured"; cause: `applyToolbarColour` assumed a single-panel layout - it took the FIRST `.lm-mod-current` tab in document order (a split layout has one current tab per tab bar) and painted the FIRST visible toolbar (`:not(.lm-mod-hidden)` matches every visible split), so the sourced tab and the painted toolbar could belong to different widgets; fix: pair per panel - for each current tab, read its colour from its live class list and colour only the toolbar inside its OWN widget node, matched via the shared widget id (the shell sets tab `data-id` to the widget id, Lumino's `Widget.id` is the widget node's DOM id); widgets without a toolbar colour nothing; `src/index.ts`
  - 2026-07-16 reported: "it tends to colour other tabs when used with API" - colours appearing on tabs/toolbars the user never coloured when claude_code drives the `setColour` API
  - 2026-07-16 root-caused: first-match `querySelector` pairing in `applyToolbarColour` breaks in split layouts; determinable from code - one `.lm-mod-current` per tab bar, several panels visible at once, and terminals have no `jp-toolbar` so the first visible toolbar is necessarily another widget's
  - 2026-07-16 fixed (pending runtime confirmation): per-panel pairing via widget id (`data-id` = widget node id); jest 11 green, lint + tsc clean; awaiting browser confirmation before marking `[x]`; see [acc-crit Active Tab Colour](acc-crit-jupyterlab-colourful-tab-extension.md#active-tab-colour)
  - 2026-07-16 runtime check on 1.1.9 failed: user reports "doesn't work" with a brown → blue → brown flicker on API-tinted tabs; the flicker is a second, interacting defect (DEF-5 - the menu map fighting the API colour on the tab itself), which also corrupts the toolbar colour every cycle; re-verify DEF-4 after the DEF-5 fix

## Colour paths

- [ ] `DEF-5` **API-tinted tab flickers between two colours and stale menu colours land on tabs the user never coloured** - HIGH; a tab tinted via the public `setColour` API (claude_code) visibly oscillates between the API colour and an old menu colour (observed brown → blue → brown in dark theme), and freshly opened terminals inherit colours the user never set; cause: two writers fight over one DOM attribute - the API colour renders from `title.className` on every Lumino tab re-render, while `refreshAllTabColours` re-applies the localStorage menu map on every mutation via `applyTabColour`, which strips ALL colour classes (including the API's) before painting the map colour; the map entry that fuels the fight is usually STALE - stable ids for terminals are `terminal:<n>` session names, which jupyter_server reuses, so a menu colour set weeks ago on a long-closed terminal attaches to any new terminal (claude_code's included) that receives the same number; every claude_code title/status update re-renders the tab and re-triggers the cycle; fix: (1) `refreshAllTabColours` paints a stored menu colour only onto a tab with NO colour class at all - it never overwrites a live colour, killing the oscillation; (2) the public `setColour` API with a non-null colour takes ownership - `releaseMenuColour` deletes the stored menu entry for that widget's tab (matched via tab `data-id`) and persists, so the stale colour cannot resurface when the API colour is later cleared; precedence is now API over menu for API-managed tabs; `src/index.ts`
  - 2026-07-16 reported: "the colour flickered, brown -> blue -> brown" when the colour was set via the API by claude_code; earlier report "tends to colour other tabs when used with API" is the same stale-map mechanism
  - 2026-07-16 root-caused: `refreshAllTabColours` unconditionally repaints map colours over API colours while Lumino re-renders the title colour on every tab update - a two-writer loop; stale `terminal:<n>` map entries (reused session names) supply the second colour; determinable from code
  - 2026-07-16 fixed (pending runtime confirmation): refresh never overwrites a live colour + API set purges the menu entry; jest 11 green, lint + tsc clean; awaiting browser confirmation before marking `[x]`; see [acc-crit Active Tab Colour](acc-crit-jupyterlab-colourful-tab-extension.md#active-tab-colour)

- [ ] `DEF-6` **a completely fresh tab inherits a dead tab's colour** - HIGH; a brand-new launcher, or a brand-new plain shell with no Claude involved, opens already tinted (peach reported); nothing to do with the API - this is the menu-driven localStorage map keyed on a RECYCLABLE slot; cause: `getStableTabId` (`src/index.ts`) resolves in three tiers and the last two are not identities - a terminal keys on `terminal:<session name>`, and terminado's `_next_available_name` counts from 1 returning the first name NOT currently in use, so closing Terminal 3 frees the name and the next new terminal IS "3" and reads `terminal:3`'s stored colour; every other widget (launcher, settings) falls through to the RAW widget id, which is a per-browser-session counter - verified live: launcher tabs carry `data-id` `launcher-0` / `launcher-1` / `launcher-2` with an EMPTY `title` attribute, so the first launcher of every session is always `launcher-0` and always re-reads that key; no cleanup exists to age entries out (1.1.3 removed the restore-time cleanup because it deleted colours before identifiers resolved), so the entries are immortal; only file tabs are safe (they key on the path, a real identity); fix: never persist under a non-identity - drop the raw-widget-id tier from storage, and drop a terminal's entry once the server stops listing that session name (after `app.restored` so the 1.1.3 trap is not re-introduced); `src/index.ts`
  - 2026-07-17 reported: "new tabs (completely new ones) are acquiring peach colour" then, narrowing it, "new tab (launcher or just fucking shell, no claude)" - ruling out the Claude auto-colour path investigated the day before
  - 2026-07-17 root-caused: proved both recycling mechanisms rather than inferring - terminado's `NamedTermManager._next_available_name` read from source (counts from 1, first free name wins → names recycle), and launcher widget ids read from the LIVE lab over CDP (`launcher-0`/`-1`/`-2`, empty title attr → falls to the raw-id tier); user's own framing was right: a file path is a true identity, a terminal number and a widget id are not, and no PID resolver is possible here (frontend-only extension, no server component, no `/proc`) - nor would PID help, since terminado exposes no UUID at all and the recyclable name IS the server-side identity
  - 2026-07-17 acc-crit: user set the bar - "new fresh tab must be clear"; recorded as [Tab Identity and Colour Persistence](acc-crit-jupyterlab-colourful-tab-extension.md#tab-identity-and-colour-persistence)
  - 2026-07-17 fixed (pending runtime confirmation): two halves - (1) `stableTabId` returns null for any tab with neither a file path nor a terminal session, so the raw-widget-id tier no longer reaches storage (the tab is still coloured in the DOM, the colour just dies with the session); (2) `pruneDeadTerminalColours` drops `terminal:` entries the server stops listing, driven by `app.serviceManager.terminals.runningChanged` - server-authoritative, so a tab closed while its session lives keeps its colour, and file paths are never touched; the pure logic is extracted to `src/identity.ts` (JupyterLab-free, jest-executable, 100% covered) because the existing suite could not run it - `src/__tests__/jupyterlab_colourful_tab_extension.spec.ts` asserts on array literals declared inside the test and imports nothing, so it would pass with the extension deleted; both fix halves MUTATION-TESTED (re-adding the widget-id identity fails 2 tests; disabling the prune fails 4), 21 jest green, lint + tsc clean; live install not possible to self-verify - `make install` depends on `increment_version` and would bump the version unbidden
  - 2026-07-17 follow-up (filed, not fixed here): `src/index.ts` remains untested - `getStableTabId`'s DOM scraping, the restore path and `applyToolbarColour` have no coverage, and the placebo spec above should be deleted or replaced
  - 2026-07-17 residual gap (accepted, architecture decision pending): the prune only catches a WITNESSED death; if terminal 3 dies and its name is reused entirely while the page is closed, the new terminal 3 still inherits the colour - at reload it is indistinguishable from the old one, since the frontend model is literally `{name: string}` and the server adds only `last_activity` (which advances for both, so it cannot disambiguate); investigated minting our own id at user's prompt and it does not work from the frontend - an id is only as durable as whatever carries it, and after a page reload you must look it up BY a stable identity, which is the thing that is missing (circular); JupyterLab hits the same wall and settles on the same two tiers - its `WidgetTracker.restore` uses `name: e => e.context.path` for every file-backed widget and `name: e => e.content.session.name` for terminals (verified in the built lab bundle), so it conflates a recycled terminal identically; the only correct fix is a server extension, the sole observer whose lifetime brackets the terminals' - rejected for now against the project's frontend-only architecture, for a narrow window
